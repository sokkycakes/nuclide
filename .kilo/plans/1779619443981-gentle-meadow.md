# H3 Menu – RmlUI + Lua Reimplementation Plan (HTML5 as Source of Truth)

## Summary
Reimplement the existing high-fidelity HTML5 Halo 3 main menu (`web/h3-main-menu/`) as a production-quality RmlUI + Lua interface. The HTML5 version (extracted from H3EK tags) serves as the definitive source of truth for layout, styling, animation timing, data structure, and interaction behavior.

## Objectives
- Achieve **visual and functional parity** between the HTML5 mockup and the RmlUI implementation.
- Produce a maintainable, data-driven RmlUI menu that can be loaded by FTE’s RmlUI context.
- Establish a repeatable testing methodology so future UI ports can follow the same parity standards.
- Deliver a clean separation between markup (`.rml`), styling (`.rcss`), data (`.lua` / JSON), and logic (`app.lua` / `main.lua`).

## Current State Assessment
- **HTML5 Source of Truth**: `web/h3-main-menu/` — `index.html`, `style.css`, `app.js`, `data.json`, full asset set, controller-style keyboard mapping.
- **Existing RmlUI Attempt**: `web/h3-main-menu-rml/` — partial port with significant RCSS parsing failures (gradients, `decorator`, modern CSS syntax, animations, grid, etc.).
- **Tooling**: `tools/css_to_rcss.py` and `build_assets.py` already exist and should be leveraged or extended.

## 1. Development Roadmap

### Phase 1 – Foundation & Tooling (1–2 weeks)
- U1.1 Audit HTML5 structure: identify all screens, pages, lists, buttons, prompts, and data bindings.
- U1.2 Extend or replace `css_to_rcss.py` to handle known incompatible properties.
- U1.3 Create asset conversion pipeline (SVG → PNG, font subsetting, texture atlas generation).
- U1.4 Define RmlUI document structure (`h3_main_menu.rml`) with clear view/page hierarchy matching the HTML5 `#screen` / `.page` model.
- U1.5 Set up Lua data model mirroring `data.json` (or load it directly).

### Phase 2 – Core Menu Screen (2–3 weeks)
- U2.1 Port main menu list (9 items, ordering, focus, wrap behavior).
- U2.2 Implement list row skinning (focused / unfocused states, colors, subtle pulsate animation).
- U2.3 Port title/Bungie logos, background layers, black fade overlay, and bottom gradient.
- U2.4 Implement slide-up entry animation and fade-in timing from H3EK animation definitions.
- U2.5 Wire basic keyboard/controller input (Up/Down, A/Enter, B/Esc) using RmlUI event listeners + Lua.

### Phase 3 – Secondary Screens & Flows (3–4 weeks)
- U3.1 Settings prompt (offline + online).
- U3.2 Friends prompt (online only).
- U3.3 Stub submenus for each main menu item (using existing HTML5 destinations as reference).
- U3.4 Roster / party UI components (list widgets, rank trays, party bars).
- U3.5 Debug HUD toggle and online state simulation.

### Phase 4 – Polish, Responsiveness & Performance (2 weeks)
- U4.1 4:3 / 16:9 / ultrawide safe-area handling (letterboxing + dynamic scaling).
- U4.2 Asset scaling strategy (nearest-neighbor vs bilinear, dp-ratio handling).
- U4.3 Animation timing parity (333 ms slide, 666 ms cubic-bezier panels, 2 s subtle pulsate).
- U4.4 Memory / texture budget review for FTE integration.
- U4.5 Controller navigation polish (focus ring, sound hooks if available).

### Phase 5 – Integration & Packaging
- U5.1 Move final assets into `base/ui/rml/h3/` (or appropriate VFS path).
- U5.2 Create loader (cvar or QC `Rml_LoadDocument`) — out of scope for v1 but planned.
- U5.3 Update AGENTS.md with H3 menu conventions.

## 2. Rigorous Testing Strategy

### Visual Parity Testing
- Automated screenshot comparison at multiple resolutions (1280×720, 1920×1080, 2560×1440) and aspect ratios (4:3, 16:9, 21:9).
- Pixel-diff threshold: < 3% difference in non-animated regions; < 8% in animated regions.
- Manual side-by-side review checklist for typography, color, spacing, and bevels.
- Reference images stored in `web/h3-main-menu/reference-screenshots/` under version control.

### Functional Parity Testing
- Keyboard + controller input matrix (all documented controls in README).
- State machine coverage: focus movement, wrap behavior, submenu opening/closing, back navigation.
- Data binding verification: list population, label text, version string, build text all match `data.json`.
- Animation timing validation (frame-by-frame or high-speed recording).

### Responsiveness & Scaling
- Test matrix: 4:3, 16:9, 21:9 at 720p / 1080p / 1440p.
- Asset scaling test: verify no pixelation on UI elements when `dp-ratio` changes.
- Safe-area test: ensure no critical UI elements are cut off in letterboxed modes.

### Lua / RmlUI Specific
- Unit tests for `lib/listcontroller.lua`, `lib/timers.lua`, and data loading.
- Memory leak checks on repeated document load/unload (`menu_restart` cycles).
- Event listener coverage (no orphaned listeners).

## 3. Source-of-Truth Methodology

1. **Reference Capture**
   - Run HTML5 version in Chrome at exact target resolutions.
   - Capture full-window screenshots + DevTools “Computed” styles for key elements.
   - Export `data.json` structure as canonical data contract.

2. **Comparison Process**
   - For every RmlUI commit that touches visuals, run automated screenshot diff against reference set.
   - Any failure > threshold triggers manual review.
   - Maintain a living “Parity Checklist” Markdown file in `web/h3-main-menu-rml/` updated per milestone.

3. **Change Control**
   - Any deviation from HTML5 behavior must be explicitly documented with justification (e.g., “RmlUI does not support X → used Y workaround”).
   - All workarounds are reviewed for visual acceptability.

## 4. Parity Success Criteria

| Category              | Criterion                                                                 | Measurement Method                  | Pass Threshold          |
|-----------------------|---------------------------------------------------------------------------|-------------------------------------|-------------------------|
| **Visual**            | Color, typography, spacing, bevels match HTML5                            | Side-by-side + pixel diff           | < 3% diff (static)      |
| **Layout**            | All elements respect 4:3/16:9 safe areas; no clipping or overlap            | Automated layout test + manual      | Zero critical issues    |
| **Animation**         | Timing and easing curves match H3EK definitions within 50 ms              | High-speed recording analysis       | ±50 ms tolerance        |
| **Interaction**       | Keyboard/controller input produces identical state changes                | Input matrix test suite             | 100% coverage           |
| **Data**              | All labels, counts, and version strings match `data.json` exactly         | Automated string comparison         | 100% match              |
| **Responsiveness**    | UI remains usable and proportionally scaled on 4:3 → 21:9                 | Multi-resolution test matrix        | No clipping, readable   |
| **Asset Fidelity**    | Textures and fonts render at correct resolution without distortion        | Visual inspection + scaling test    | Nearest-neighbor match  |
| **Performance**       | Document load < 200 ms, 60 fps on target hardware                         | In-engine profiling                 | < 200 ms / 60 fps       |

## Risks & Mitigations
- **Risk**: RmlUI parser limitations block complex CSS. **Mitigation**: Use `css_to_rcss.py` + manual RCSS author review; maintain `style-preview.rcss` for live viewer.
- **Risk**: Animation timing cannot be perfectly matched. **Mitigation**: Document acceptable variance (±50 ms) and validate with high-speed capture.
- **Risk**: Asset scaling differs between HTML5 and RmlUI. **Mitigation**: Establish explicit `dp-ratio` handling rules early.

## Deliverables
- Production `h3_main_menu.rml` + `style.rcss` + supporting Lua files in `base/ui/rml/h3/`.
- Automated test harness + reference screenshot suite.
- Living “Parity Checklist” and deviation log.
- Final report confirming all success criteria met.

This plan ensures the RmlUI implementation is not just “close enough” but rigorously validated against the authoritative HTML5 source of truth.
